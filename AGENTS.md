## 1. Project Overview & Tech Stack

This project is a production-grade, event-driven REST API written in Go following Clean Architecture.

- **Language**: Go 1.26+
- **Router**: `github.com/go-chi/chi/v5`
- **ORM & Database**: `gorm.io/gorm` with PostgreSQL (`gorm.io/driver/postgres`)
- **Cache & Session**: `github.com/redis/go-redis/v9`
- **Dependency Injection**: `github.com/google/wire`
- **Validation**: `github.com/go-playground/validator/v10`
- **Schema Migration**: `github.com/pressly/goose/v3`
- **Messaging**: NATS JetStream (`github.com/nats-io/nats.go`)
- **API Documentation**: OpenAPI / Swagger with `github.com/swaggo/swag`
- **Observability**: OpenTelemetry metrics & tracing, structured logging with `log/slog`

## 2. Architecture & Directory Map

> Detailed guide: [docs/architecture.md](docs/architecture.md)

The repository enforces strict layered architecture with unidirectional flow:
`Router` -> `Handler` -> `Usecase` -> `Repository` -> `Entities / Database`

```
├── cmd/
│   ├── http/                   # HTTP server entrypoint & wire configuration
│   │   ├── main.go
│   │   ├── wire.go
│   │   └── wire_gen.go         # Auto-generated by Wire
│   └── worker/
│       └── mail/               # Asynchronous event worker entrypoint
├── docs/                       # Technical subsystem specifications
├── internal/
│   ├── config/                 # Environment configuration structs & loading
│   ├── core/
│   │   ├── domain/
│   │   │   ├── dto/            # Response objects returned to client
│   │   │   ├── entities/       # GORM persistence models
│   │   │   └── payloads/       # Incoming HTTP request payload structs with validation tags
│   │   ├── handler/            # HTTP transport layer: decoding, validating, calling usecase
│   │   ├── repositories/       # Data persistence layer using GORM & TxManager
│   │   └── usecase/            # Business logic, authorization checks, transactions, events
│   ├── dependency/             # Google Wire provider sets and App initialization struct
│   ├── messaging/              # NATS JetStream publisher, topics, and event payloads
│   ├── middleware/             # Chi HTTP middlewares (Auth, RBAC, Tracing, CORS, RateLimit)
│   ├── pkg/                    # Reusable adapters (auth, cache, database, health, nats, storage, telemetry)
│   ├── router/                 # Chi route registration and grouping
│   ├── utils/
│   │   ├── constants/err/      # Centralized error codes and error response mapping
│   │   ├── enums/              # Domain enums (Status, etc.)
│   │   ├── errors/             # AppError custom error type
│   │   ├── helper/             # Query filter/sort/pagination and string helpers
│   │   ├── request/            # Request decoding helpers (DecodeJSON, PathInt64, List)
│   │   ├── response/           # Standardized JSON response helpers
│   │   └── validator/          # Custom validator rules (password complexity, etc.)
│   └── worker/                 # Worker handlers and consumers
├── migrations/                 # Goose SQL migration files
└── tests/
    └── integration/            # End-to-end and integration tests
```

## 3. Core Invariants & Rules for AI Agents

1. **Layer Boundary Enforcement**:
   - Handlers NEVER access database or repositories directly. Handlers only call Usecase.
   - Usecases NEVER deal with `http.ResponseWriter` or `*http.Request`.
   - Repositories NEVER validate HTTP payloads or handle business orchestration.
2. **Standardized Error Handling**:
   - Detailed guide: [docs/error-handling.md](docs/error-handling.md)
   - NEVER return raw errors (`fmt.Errorf`, `errors.New`) directly to HTTP handlers or responses.
   - ALL business and validation errors MUST use `apperror.New(errconstant.ErrCode..., err)`.
   - ALL new error codes MUST be registered in `internal/utils/constants/err/messages.go`.
   - Handlers MUST render errors via `response.ErrorResponse(w, err)`.
3. **Database Transactions**:
   - Detailed guide: [docs/database-transactions.md](docs/database-transactions.md)
   - When modifying multiple tables or entities, execute inside `TxManager.WithTx(ctx, func(txCtx context.Context) error { ... })`.
   - Repositories read the active transaction automatically via `repo.DB(ctx)`. Always pass `ctx` down intact.
4. **Optimistic Locking**:
   - Entities subject to concurrent edits MUST have a `Version int64` field.
   - Initial entity creation MUST explicitly set `Version: 1` so in-memory responses match the database default.
   - Updates and soft-deletes MUST check `Where("version = ?", version)` and increment `version = gorm.Expr("version + 1")`.
   - If `RowsAffected == 0`, return `apperror.New(errconstant.ErrCodeStaleResource, nil)`.
   - In repository update methods, ALWAYS increment `entity.Version++` in Go memory after successful update (`RowsAffected > 0`) so usecase responses carry the latest version to the client.
   - Response DTOs MUST include `Version int64` (`json:"version"`) so clients know the current version for subsequent mutation requests (`Update...Request`, `MutationRequest`).
5. **Request & Response Consistency**:
   - Detailed guide: [docs/api-conventions.md](docs/api-conventions.md)
   - Decode JSON with `request.DecodeJSON[PayloadStruct](r)`.
   - Parse route parameters with `request.PathInt64(r, "id")` or `request.PathParam(r, "slug")`.
   - Parse list queries with `request.List(r)`.
   - Return single items with `response.Success(w, http.StatusOk, data)`.
   - Return paginated lists with `response.SuccessResponse(w, items, total, params.Skip, params.Limit)`.
6. **Code Generation & Sync**:
   - After modifying `Dependencies` structs or `internal/dependency/provider.go`, ALWAYS run `make wire`.
   - After adding or modifying handler godoc annotations, ALWAYS run `make swagger-gen`.
   - Never edit `wire_gen.go` or `docs/swagger/*` manually.
7. **Migrations**:
   - Detailed guide: [docs/database-transactions.md](docs/database-transactions.md)
   - NEVER alter an existing, executed migration file.
   - Create new migrations using Goose format (`-- +goose Up` and `-- +goose Down`) in `migrations/`.

## 4. Step-by-Step: Implementing a New Module / Feature

> Detailed guide & complete code templates: [docs/module-development.md](docs/module-development.md)

Follow this checklist when adding a new domain entity or feature (e.g., `Product`):

| Step | Action | Location |
|---|---|---|
| **1** | Database Migration | `migrations/<timestamp>_create_<table_name>.sql` |
| **2** | Entity Model | `internal/core/domain/entities/<module>.go` |
| **3** | Payloads | `internal/core/domain/payloads/<module>.go` |
| **4** | DTO | `internal/core/domain/dto/<module>.go` |
| **5** | Error Codes | `internal/utils/constants/err/messages.go` |
| **6** | Repository | `internal/core/repositories/<module>.go` |
| **7** | Usecase | `internal/core/usecase/<module>.go` |
| **8** | Handler | `internal/core/handler/<module>.go` |
| **9** | Router | `internal/router/<module>.go` & mount in `router.go` |
| **10** | Wire Generation | Run `make wire` |
| **11** | Swagger Generation | Run `make swagger-gen` |
| **12** | Tests & Verification | Run `go test -count=1 ./...` |

## 5. Security & Authorization Guidelines

> Detailed guide: [docs/auth.md](docs/auth.md)

- **Authentication**: Apply `appmiddleware.Auth(deps.JWT, deps.Session)` on protected route groups.
- **Accessing User Context**: Use `auth.GetClaims(r.Context())` to retrieve `UserID`, `SessionID`, `Roles`, and `Permissions`.
- **Role Guard**: `appmiddleware.RequireRole("superadmin")`
- **Permission Guard**: `appmiddleware.RequirePermission("users:create")` or `appmiddleware.RequireAnyPermission("users:read", "admin:access")`.
- **Password Hashes**: Use `auth.HashPassword(password, uc.bcryptCost())` and `auth.ComparePassword(hash, plain)`.
- **No Direct Secrets in Code**: Read configuration via `internal/config/config.go` mapped to `.env`.

## 6. Background Worker & Asynchronous Events

> Detailed guide: [docs/messaging.md](docs/messaging.md)

When publishing domain events for async background processing:
1. Define event struct and subject in `internal/messaging/events.go` and `internal/messaging/topics.go`.
2. Publish from Usecase:
   ```go
   err := uc.publisher.Publish(ctx, messaging.Event{
       Subject: messaging.SubjectUserRegistered,
       Data:    eventPayload,
   })
   ```
3. Consumer logic belongs under `internal/worker/<worker_name>/`.

## 7. Testing Strategy

> Detailed guide: [docs/testing.md](docs/testing.md)

- Co-locate unit tests in respective `tests/` directories (`handler/tests/`, `usecase/tests/`, `repositories/tests/`).
- Use `net/http/httptest` for handler testing without network overhead.
- Roll back database transactions in repository unit tests.
- Isolate end-to-end tests with `//go:build integration`.

## 8. Essential Commands Reference

| Action | Command | Notes |
|---|---|---|
| **Run Unit Tests** | `go test -count=1 ./...` | Fast, mock/isolated unit tests |
| **Run Integration Tests** | `make test-integration` | Requires Docker infrastructure up |
| **Generate Wire DI** | `make wire` | Must run after modifying provider or dependencies |
| **Generate Swagger Docs**| `make swagger-gen` | Must run after changing handler doc comments |
| **Run Migrations Up** | `make migrate-up` | Applies all pending migrations |
| **Rollback Migration** | `make migrate-down` | Rolls back the latest migration |
| **Lint Codebase** | `make lint` or `golangci-lint run` | Ensures code style and safety standards |
| **Start Local Stack** | `docker compose up -d` | Starts Postgres, Redis, NATS, MailDev, RustFS |
| **Run HTTP Server** | `make run-http` | Runs API server on configured port |
